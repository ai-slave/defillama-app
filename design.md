# Llama Design System — web app

DefiLlama is a data-dense analytics UI: near-neutral surfaces, restrained color, tight radii, small type. Color signals **state and data direction** (up/down, brand, warning), never decoration. Hierarchy comes from surface elevation and text tiers, not shadows.

Design source of truth: the **Llama Design System** Figma library (Primitives + Semantics collections). Code source of truth: [`src/styles/primitives.css`](src/styles/primitives.css) and [`src/styles/semantics.css`](src/styles/semantics.css). If this document and those files disagree, the files win; if the files and the Figma library disagree, flag it — don't silently pick one.

> **Note:** this file is excluded from Tailwind's source scanning (`@source not` in `tailwind.css`) so the class names mentioned here never generate CSS. Keep it that way.

## Architecture

Three tiers, strictly ordered. Components may only reference tier 2 (or tier-3 component tokens where they exist):

1. **Primitives** (`primitives.css`) — raw ramp values (`--blue-500`). Never used in components. Deliberately _not_ registered as Tailwind colors (names would collide with the built-in `neutral`/`blue`/… palettes).
2. **Semantics** (`semantics.css`) — role tokens (`--bg-surface`, `--text-data-up`), light values on `:root`, dark overrides under `html.dark`. Registered as Tailwind utilities: `bg-surface`, `text-primary`, `text-data-up`, `border-subtle`, …
3. **Component tokens** — only when a value genuinely diverges from a semantic (currently: chips and Yields' accessible text accents, which are intentionally darker than its chart palette in light mode). If a component token would just alias a semantic, bind the semantic directly instead.

The mode lives in the CSS selector, never in the token name: no `*-light`/`*-dark` suffixed pairs, and no `dark:*-[#hex]` utilities in components.

## File placement

Component code has three homes, chosen by ownership — not by how the file happens to be styled:

- **`src/ui/`** — design-system primitives: token-bound, no data fetching, no product knowledge, documented as a recipe in this file.
- **`src/components/`** — shared application components: composed, may know about data shapes, used by two or more products. Folders are named for their domain (`ChartExport/`, `Search/`), never for their implementation era or technique — no `ButtonStyled`-style names.
- **`src/containers/<Product>/`** — product-owned. A component consumed by exactly one product lives with that product, even if it looks generic; local shared pieces go in the product's `shared.tsx`.

When a shared component's last second consumer disappears, move it to the remaining product. No re-export shims at old paths — imports break at typecheck and get fixed in the same commit as the move.

## Class composition

Visual contracts belong to recipe components and hand-rolled variant maps (`buttonStyles({ variant, size })` over const maps — typed, zero-dependency; this is the house cva, so don't add cva). Exported class-string recipes are tagged with [`tw`](src/ui/tw.ts) — a zero-cost identity tag whose only job is putting the string inside a construct oxfmt's Tailwind sorter recognizes; interpolation inside `tw` is a type error on purpose. At call sites, `clsx` is the composer for genuinely conditional classes; plain template literals are fine for simple cases, but once a template accumulates two or more ternaries, hoist the branches into a const map (the `planHeadStyles`/`VARIANT_CLASSES` pattern) instead of growing the expression. **No class-merge libraries (`tailwind-merge`, `cnfast`), ever:** recipe components accept `className` for layout placement only, so class conflicts are designed to be impossible — a merge utility exists to make overrides _win_, which would turn recipe violations from visible bugs into silently-working forks and hollow out the ratchet.

`text-disabled` is only for actual disabled controls. Do not use it for metadata,
symbols, empty values, helper copy, or struck/excluded data; use `text-secondary`
for readable support text and `text-tertiary` for de-emphasized/missing values.
(The former `--legacy-text-disabled` alias was retired: its callers were
converted to `text-tertiary` directly.)

**Text-tier decision rule (owner decision, 2026-07-08):** if removing the text
would change what the user knows or can do, it is `text-secondary` or better; if
it only qualifies something next to it, it is `text-tertiary`. Corollaries:
(1) enabled interactive text never rests on tertiary — the standard interactive
ladder is rest `text-secondary` → hover/focus `text-primary` → active branded
(`text-link-on-tint`/`bg-brand-muted`, or underline + primary for tabs); even after the
light tertiary token was raised to the AA floor, interactive labels stay above
the de-emphasis tier.
(2) in a metric line the value sits exactly one tier above its qualifier —
`$311.138b` secondary + `7d` tertiary; qualifiers are bare spans (`24h`, `30d`),
not parenthesized text baked into the value string. Tertiary keeps: suffixes,
timestamps, counts, units, placeholders, empty/loading states, and
struck/double-counted values.

Hover washes paint _over_ `bg-surface` and are deliberately asymmetric across modes: brand-tinted in light, white-lift in dark (verified from the metrics-card hover pair and the columns-popover row). **Focus is hover-plus (owner decision, 2026-07-09):** the global `:focus-visible` base rule in `tailwind.css` draws a 2px **inset** `border-brand` ring on everything (inset so it survives full-bleed rows in overflow-hidden popovers and dense toolbars); components may keep the wash on focus as well. Two cases the base rule cannot cover use utilities: Ariakit composite rows (selects/comboboxes) bind `data-focus-visible:focus-ring` — DOM focus stays on the input, and never bind to `data-active-item`, which follows mouse hover and would show a false ring; solid brand fills use `focus-visible:focus-ring-on-brand` (white ring — a brand ring is invisible there). `outline-none`/`outline-hidden` suppress the base ring: only do that when the element has its own focus indicator (e.g. `inputStyles` uses `focus:border-brand`). Selection/active is a different concept and uses brand tokens (tint, solid, or brand border depending on the control — see Components).

**Two hover mechanisms — pick by resting background:**

- `hover:bg-hover-row` — only for elements whose resting background is **transparent** (popover/menu/table rows, ghost buttons). It _replaces_ the background, which is fine when there is nothing to replace.
- `.hover-wash` ([semantics.css](src/styles/semantics.css)) — for any element whose resting background is **tinted or opaque** (`bg-brand-muted` pills, selected segments, `bg-surface` tiles). It applies the wash as a `background-image`, stacking over the resting color. Handles `:hover` + `:focus-visible` and skips `:disabled`/`aria-disabled` automatically. Variants: `.hover-wash-card` (fainter `--hover-card`, used by interactive `Card`) and `.group-hover-wash` (washes when the ancestor `.group` is hovered — for sticky table cells that must keep an opaque bg). Never put `hover:bg-hover-row` on a `bg-brand-muted` element: light-mode `hover-row` is the _same value_ as light `bg-brand-muted` (`#1f67d21f`), so the hover is invisible, and in dark it strips the brand tint.
- Exception: an **opaque→opaque elevation step** is also a valid hover for triggers resting on `bg-surface-elevated-1` (e.g. the Select `default` trigger hovers to `bg-surface-elevated-2`) — a full-strength deliberate affordance, stronger than the wash. Don't mix both on one element.

### Usage rules

- **Surfaces** step `page → surface → elevated-1 → elevated-2`. Cards sit on `bg-surface`; elevation steps are for nested emphasis, not general fills.
- **Floating overlays are `bg-overlay`, not a ladder step.** Light-mode elevation is carried by shadow, dark-mode elevation by surface lift — so the overlay token is white in light and equals `elevated-1` in dark, and overlay recipes carry the shared elevation shadow. A darker-than-surroundings overlay reads recessed in light; the Figma library still maps overlays to `bg-surface-elevated1` (library update requested). Exception: **canvas** dialogs/drawers whose body is a grid of `bg-surface` cards (Metrics dialog, MarketMakers detail drawer) keep `bg-surface-elevated-1` — there the gray plays the same role `bg-page` plays behind page cards.
- **Text tiers rank information.** They are text-only by convention — never `bg-primary`.
- **Solid colors for text and fills; translucent for borders, dividers, and hover washes.**
- **Data direction:** `text-data-up`/`text-data-down` for movement; the `-alt` pair when a chart needs a second axis of meaning. Reserve `--success`/`--error` for genuine feedback (form validation, toasts) — a price drop is not an error.
- **Brand blue `#1f67d2` comes only from the brand tokens.** Never restate it as a hex literal.

Sizes in the table are Figma px for reference; the utilities implement them in **rem** (px ÷ 16) so user browser font-size preferences are respected — same basis as Tailwind's built-in `text-*` scale. Verified line heights follow the Figma per-style values as exact unitless fractions (`Figma line-height ÷ font-size`): Label 10/12, 12/16, 14/17; Heading 18/22; Body 12/16, 14/21. The remaining integer line boxes are owner-accepted application values rather than claims of Figma verification; a future published library measurement may supersede them explicitly. This avoids the off-center placeholder/control text that fractional band ratios caused. Vertical rhythm still belongs to containers (`gap`, `padding`, `min-h`), not arbitrary `leading-[…]` or `tracking-[…]` one-offs. (1px hairline borders and canvas chart fonts stay px on purpose.)

`label-*` (medium) carries single-line scannable text such as nav, form labels, and metadata. `body-*` (regular) is multi-line copy. Each named typography utility owns its size, weight, line height, and family where applicable; do not combine it in the same variant scope with another named type utility or a conflicting `text-*`, `font-*`, or `leading-*` utility. Standard table headers are the explicit `text-sm font-medium` recipe (14px Inter with the normal table line height), and standard table cells inherit 14px Inter. `mono-*` is reserved for deliberate metric/KPI presentation (summary cards, stat strips, and aligned financial-series blocks), addresses, and code; it is not the default for ordinary numbers. Existing custom JetBrains Mono combinations that do not exactly match the named ramp retain their measured size, weight, and line height until a deliberate visual change is approved. `tabular-nums` is reserved for changing values where proportional digits would cause visible layout jitter, such as timers, countdowns, and animated/live counters. Static table and UI numbers stay proportional Inter. Do not set arbitrary font sizes (`text-[10px]`) — the ramp has a step for every approved size.

**Size floors (owner decisions — the frames' smallest sizes read too small in the browser; don't copy Figma sizes verbatim):** interactive text (buttons, pills, selects, menu rows) is **12px minimum** (`label-sm`/`body-sm`); card body and data rows are **14px**. Metric/KPI surfaces may use `mono-md`/`mono-md-bold` values, while ordinary table data remains 14px proportional Inter. 10px (`label-xs`/`body-xs`) is reserved for non-interactive metadata — eyebrow section headers and count badges. A deliberately compact table may use 12px only when its complete density recipe calls for it; never shrink headers or rank values independently.

## Spacing, radius, borders

- **Spacing** is a 4px-based scale — the standard Tailwind scale; no arbitrary `p-[10px]` values (ratcheted by the design-token policy check).
- **Border width** is 1px in almost all cases. Data-table row/grid dividers use `border-subtle` (the opaque `border-divider` token was retired — it matched elevated-1/elevated-2 exactly and vanished on elevated surfaces); section separators and detail-card internal rules use `border-subtle` or `border-very-subtle` depending on the surface contrast. Do not use `border-medium` for simple dividers.
- **Layout is gap/padding/min-h driven.** Figma values for margins, absolute offsets, and per-element line heights are rendering artifacts of the design tool — do not transcribe them. Space siblings with flex/grid `gap`, size boxes with `padding` and `min-h`, and let text wrap naturally. Margins are reserved for opting out of a parent's rhythm (`mt-auto`, negative bleed), not for building it.
- **Responsive spacing picks both ends from the palette** (`gap-2 lg:gap-4`), never an invented in-between value. Viewport-fluid scaling (Utopia-style `clamp()` interpolation) was considered and rejected: this is a density-first data app — big screens get more data, not bigger chrome — and fluid values would break pixel-diff verification and Figma-frame review.

### Intentional Design Reconciliations

These are owner decisions, not extraction mistakes:

- Interactive text never goes below 12px even when Figma shows 10px controls or chips. Use `label-sm`/`body-sm`; reserve `label-xs`/`body-xs` for non-interactive metadata.
- Card body/data rows stay 14px for browser readability, even where a frame uses 12px.
- Dense stat/data cards use 8px padding on all sides. Some Figma cards show 12px vertical padding; code should prefer the 8px dense-card rhythm unless a route-specific frame requires the extra space.
- Home/analytics page stacks use 8px major gaps. Some home frame siblings measure as 6px; the implementation should use one page-level `gap-2` rhythm and keep the top controls' 12px horizontal gap as the explicit exception.
- Chart/table/action toolbars use 32px controls from primitive padding/min-height. Dense adjacent controls use 6px gaps; larger control groups and toolbar padding use 8px.
- Nested scroll containers inherit the compact scrollbar recipe globally from `:where(body *)`; the native `html`/`body` document scrollbar is intentionally unchanged. Do not add a local `thin-scrollbar` class. Use `scrollbar-none` only for an explicit hidden-scrollbar interaction such as a swipeable chip track.
- Titled `PanelHeader` remains the taller titled-panel recipe. Inline chart/table toolbars use the compact toolbar recipe instead of forcing every chart control row into `PanelHeader`.
- Anchored-surface gutters: menus use `gutter={8}`, anchored selects/popovers/hovercards use `gutter={6}`, nested submenu flyouts use `gutter={4}`; text tooltips keep the Ariakit default.
- Popover/menu surfaces own background, border, radius, and overflow only. Search blocks, action rows, footers, and list rows own vertical spacing.
- Cartesian ECharts geometry uses the shared [`chartSpacing.ts`](src/components/ECharts/shared/chartSpacing.ts) recipes. `chartGrid()` treats 8px as the visual outer bound through ECharts `outerBounds`; legends, scroll paging, and dataZoom use the documented optical compensation in that module. Do not recreate those values at call sites or add DOM body padding around cartesian charts.

## Component recipes

These recipes are the shared component vocabulary established from the reviewed application designs and current implementation; build them once and reuse them everywhere.

- **Button** — [`src/ui/Button.tsx`](src/ui/Button.tsx). Heights are **padding-driven, never fixed** (every control in a row shares the same `py`, so mixed content always lines up): `sm` = `min-h-6 px-2 py-0.5 rounded-md`, `md` = `min-h-8 px-3 py-1.5 rounded-lg`, both `label-sm`; icon-only (`square`) = `p-0.5`/`p-1.5`. Variants: _secondary_ = transparent + `border-medium`; _primary_ = `bg-brand text-on-brand`; _outline_ ("active = branded") = `border-brand text-link`; _filter_ = full-radius `border-brand text-primary` with active `bg-brand-muted` for metrics-directory filter pills; _toggle_ = elevated neutral resting fill with a brand border/tint/`text-link-on-tint` active state for toolbar filters and selectable options; _metricBrowse_ = 6px-radius dashed brand selected pill in the home metrics browse toolbar; _ghost_ = quiet borderless trigger with a brand-muted fill and text-link-on-tint while `data-active=true`; use an additive hover wash so the active tint persists. Disabled and aria-disabled controls do not change their fill or brightness on hover. Variants never inject icons: callers may add a leading icon when the interaction needs one, while text-only toggles use the same variant unchanged. Callers must choose `size` explicitly. Compose into Ariakit via `render={<Button size="md" />}`; `buttonStyles({ size: 'md' })` only for class-only hosts. **Control icon sizes (owner decision, 2026-07-10):** an icon sitting **beside a label** inside a control is 14px (`size-3.5` / `height={14}`) — 16px next to the 12px `label-sm` control text reads oversized (export buttons and `ExternalLinkButton` are the reference). **Icon-only** `square` controls use 16px (`size-4` / `height={16}`) — pagination chevrons, dialog close, the protocol header's ghost globe/bookmark. Don't mix the two roles' sizes.
- **External link pill** — [`src/components/ExternalLinkButton.tsx`](src/components/ExternalLinkButton.tsx) is the app-wide grammar for external links presented as buttons: optional 14px brand icon left (`globe`, `github`, `twitter`, …), label, 14px `arrow-up-right` right, on `buttonStyles({ size: 'md' })`. Multi-URL cases (several websites, audit reports) use `Menu isExternal` with the same `buttonStyles` class instead. Do not hand-roll icon+label+arrow anchors.
- **Chain pill** — `rounded-sm px-2 py-1 body-sm font-medium`, resting `bg-brand-muted text-link-on-tint`; active `bg-brand text-on-brand`; hover/focus = `hover-wash`; row container `bg-surface border-subtle rounded-lg p-1 gap-1` clipped to exactly one row. (`font-medium` is an owner decision: the frame's 10px-Regular pill text was rejected with the same file-artifact reasoning as its size; uniform weight also keeps pill widths stable across active/inactive.) `text-link-on-tint` = `text-link` in light but a lighter interim blue (`#6a9be0`) in dark, because dark `Text/links` is below AA on `bg-brand-muted` — collapses back into `text-link` once the library fixes the token (design ask below). The "Others" overflow trigger is `bg-surface-elevated-2` + `hover-wash`.
- **Segmented control (Tabs)** — wrapper `bg-surface border-medium rounded-lg p-0.5 gap-0.5`; items `px-2 py-1 body-sm rounded-md` (the wrapper's `min-h` size pins control height — `py-1.5` would push content past the `sm`/24px floor), selected `bg-brand-muted text-link-on-tint`, unselected `text-secondary` with `hover:text-primary`; hover/focus = `hover-wash`. This is the standard toolbar segmented control for chart periods, denominations, table metric/period filters, and view-mode switches. Source designs disagree on unselected item size/color; the application treats unselected items as readable interactive text above the de-emphasis tier.

  **Semantics are a separate decision from the look** (`semantics` prop, owner decision 2026-08-06): the same visual control serves two different jobs and must announce the right one. `radio` (default) is for picking a **value that reconfigures one region** — a period, a denomination, a chart metric, a table's grouping; nothing appears or disappears, so a radiogroup is the honest model. `tabs` is for switching between **distinct content panels** (RWA platform Assets/Peers/Asset mix/Information, Token Rights Overview/Details): it emits `role="tablist"`/`role="tab"` + `aria-selected`, and pairs with `segmentedControlTabIds(prefix, value)` so each tab carries `id`/`aria-controls` and its panel carries `role="tabpanel"` + `aria-labelledby`. Without that pairing assistive tech cannot tell that the region below changed, or reach it. `aria-controls` is set only on the selected tab because unselected panels are not mounted. Keyboard behavior is identical either way — the roving tab stop with arrow-key selection is already the tab pattern with automatic activation. Do **not** convert value-pickers to tabs to make them uniform; uniform roles on non-uniform behavior is the bug, not the fix. Page-level route navigation stays with the underline [`Tab`](src/ui/Tab.tsx) recipe, never this control.

- **Joined toggle group** — wrapper `border-subtle rounded-md` (6px), no padding; segments `px-2 body-sm`, selected segment solid `bg-brand text-on-brand`. - **Hover content: Tooltip vs Hovercard vs Popover.** Plain short text → [`Tooltip`](src/ui/Tooltip.tsx) on `tooltipSurfaceStyles` (`rounded-md`, 6px — radius follows component size). Structured or long contextual content (lists, breakdowns, definitions, previews) → [`Hovercard`](src/ui/Hovercard.tsx) on the hovercard surface (`rounded-xl`) — unlike a tooltip it can be hovered into, dismissed with Escape, reached by keyboard, and opened by tap/click (WCAG 1.4.13). Use a popover/menu/dialog instead when opening the surface is the primary action or the content is a task-oriented form or control set; a contextual hovercard preview may contain a small number of links or actions when keyboard and touch access remain intact. When the original anchor has its own click action, keep that action independent and provide a separate labeled info control unless the contextual preview intentionally supports that action. `Tooltip` opens on tap because touch has no hover, whatever element `render` makes the anchor; the one exception is a `render` anchor that is, or sits inside, a link, button, or other control, where the tap keeps that control's action. Do not stuff data into native `title=` attributes — they are unreachable on touch and unstyled; icon-only controls need `aria-label` plus a `Tooltip`. The "N chains" list uses the shared `ProtocolChainsHovercard`.
  The `Hovercard` anchor is `inline-flex`: it sizes to its content and follows the parent's `text-align`, so a table cell's `align` positions it. Do not add `ml-auto`, `w-fit` or another display class to place it; `inline-flex` sorts after the other display utilities and always wins. Truncating text goes in an inner `<span className="truncate">` with `max-w-full` on the anchor, a bar that fills its cell adds `w-full`, and an anchor with no text (a pie, a bar) adds `align-middle` so it does not sit on the text baseline.
  Hovercard viewport safety and content width are separate contracts. The shared surface caps itself with Ariakit's `--popover-available-width` and `--popover-available-height`, and the shared `Hovercard` keeps 16px from viewport edges. Each consumer owns its readable preferred width: compact vertical lists use intrinsic `w-max`; prose and ordinary structured cards generally use `w-80`; dense financial breakdowns may use `w-96`; wide wrapping collections may use a larger local maximum. Combine a preferred width with `max-w-(--popover-available-width)`, and use available height plus internal scrolling for long content. Do not reproduce anchored-surface safety with `calc(100vw - …)`; viewport calculations remain valid for centered dialogs and mobile drawers that are not sized as anchored surfaces.

- **Table** — two row modes: normal rows default to 50px; compact rows default to 40px. `rowSize` is an explicit content-driven override for multiline/entity rows and must be used by both rendered CSS and the virtualizer estimate. Compact mode also removes vertical grid dividers and uses its tighter padding; it is not permission to shrink one cell or header independently. Rows use `border-subtle`; headers use 14px proportional Inter via `text-sm font-medium`; body cells inherit 14px proportional Inter. Numeric columns use normal cell alignment (usually right-aligned) without `mono-*` or `tabular-nums`; changing timers/countdowns/live counters are the documented exception. The active sort caret uses `text-brand` and inactive carets use `text-tertiary/50`; row hover uses `bg-hover-row`. Toolbar controls are always `md`/32px in table contexts: no local `px-2 py-1.5 text-xs`, no implicit/default `sm`, and no fixed-height wrapper hacks. `TableToolbar`/`TableToolbarControlGroup` provide `p-2` toolbar padding and 6px dense internal gaps; callers that need distinct left/right action groups wrap those groups and use `gap-2` between groups. **Toolbar alignment (owner decision, 2026-09-26):** `TableToolbar`, `TableToolbarControlGroup` and `PanelHeader` own `justify-end`, so controls hug the right edge at every width; callers never pass `justify-*` (the `toolbar-justify-override` rule in `check-design-tokens.mjs` counts it). The one left-side item — the search (`searchFieldWrapperStyles` carries `mr-auto`), a `PanelTitle`, a `label-md` title, or a leading view switch — takes `mr-auto` and sits first. Below `sm` the search fills its own row and every other control keeps its natural width, wrapping under it on the right: no `max-sm:flex-col` groups, no `max-sm:w-full` controls, and selects use `variant="filter"`. A labeled chip row (`Filters: + Has Burns · + Has Dividends`) is not a toolbar: render it as its own left-aligned `role="group"` row (`flex flex-wrap items-center gap-1.5`, `px-2 pb-2` under a toolbar, `p-2` alone; leading label `mr-1 label-sm text-secondary`; chips are `md` toggles), not inside `TableToolbar`. Don't add wrapper divs a toolbar does not need: a lone title is `<h2 className="mr-auto label-md">`, and `w-full` on a toolbar is a no-op. Table metric/period/view groups use the standard tinted segmented control, not the solid joined-toggle exception. Heading hierarchy:
  - Primary table is the page: use `PanelHeader` + `PanelTitle as="h1"` with md controls. Compose these inside `SearchTableProvider`; use `TableSearchInput` and the appropriate search table view. See [ADR 0007](docs/adr/0007-composed-searchable-tables.md).
  - Page already has a real h1/hero above: do not add another table title. Use compact `TableToolbar` with search/filters only, still md controls.
  - Secondary/embedded table: use compact `TableToolbar` + existing `label-md` title, or no visible title if the surrounding section already labels it.
- **Paginated tables** — `PaginatedTable` owns pagination/scroller behavior but no border: the page's surrounding `Panel`/`Card` is the table's only rounded border. The pagination row is attached to the table with `border-t border-subtle p-2`; do not add a detached page-local footer or a gap between the scroller and pagination. Window-sticky headers are opt-in via `stickyHeader`; use them only for long paginated directories that materially benefit from persistent column context (currently `/tokens`). Other paginated tables retain their normal non-sticky header.
- **Tab navigation (page-level)** — items `px-3 py-2 label-md`, inactive `text-secondary` with `hover:text-primary`, active `text-primary` + 2px `bg-brand` underline bar with rounded top corners.
- **Icon color** — three roles: (1) _affordance indicators_ (select/column-header/accordion/row-expand chevrons, resting sort carets, help circles, drag handles) pin `text-tertiary` — never ship a colorless icon that inherits whatever text tier surrounds it; (2) _icons beside a label in the same control_ (button icons, link arrows, leading icons) inherit `currentColor` deliberately so they move with their label on hover/active; (3) _icon-only action buttons_ (copy, close ✕, csv/download, settings, pagination arrows) use the ghost ladder `text-secondary` → hover/focus `text-primary` — never opacity dimming. Status icons use semantic tokens (`text-warning`, `text-data-down`); empty-state illustrations are `text-tertiary`; the active sort caret stays `text-link`. `QuestionHelper` and the `Ariakit.SelectArrow` hosts pin tertiary centrally.
- **Active = branded** is the cross-component rule: selection is shown with brand tint/solid/border + link-blue text, never with grays.

## Charts

Chart **series** colors come from `CHART_COLORS` + `getNDistinctColors` (golden-angle generator) in code — they are intentionally _not_ design tokens and must not be bulk-changed; the Figma library has no N-series concept.

Chart **canvas chrome** (axis labels, gridlines, legends, dataZoom, PNG-export framing, and candlestick direction colors) uses the `--chart-*` tokens in `semantics.css`. The chart-theme pass established these as the current visual baseline: axis labels use the tertiary tier, gridlines share the low-alpha chart stroke, and candlesticks use the chart direction tokens. ECharts HTML tooltips are DOM surfaces instead: options set transparent native chrome and the shared `.defillama-echarts-tooltip` recipe in `tailwind.css` applies the overlay, border, text, radius, and shadow tokens. Chart tokens remain separate from series palettes so later semantic-token changes cannot silently recolor chart data.

Chart **geometry** uses [`src/components/ECharts/shared/chartSpacing.ts`](src/components/ECharts/shared/chartSpacing.ts). Standard cartesian grids have an 8px visual inset on every side via `outerBoundsMode: 'same'` and `outerBoundsContain: 'axisLabel'`; a default legend starts 8px from the top and reserves 40px before the plot; scroll legends reserve a 16px right gutter and use the same active/inactive color hierarchy as table sort carets. Slider dataZoom uses a fixed height and compensates for ECharts handle overflow so its visible left/right inset is 8px and its visible bottom inset is 12px. Consume the exported recipes/constants instead of copying raw grid, legend, or slider offsets.

Non-cartesian and alignment-sensitive charts keep explicit exceptions. Treemaps use an 8px **canvas-wrapper** inset because ECharts zoom clips to the canvas rather than the series rectangle; do not replace it with series offsets or remove it after checking only the unzoomed state. Legend-based pies stay vertically centered and reserve their measured legend region; external-label pies may pass an explicit `centerY` (the bridged composition uses `44%`) so the complete pie-plus-label composition is centered without changing every pie. Stacked candlestick grids keep one fixed left edge across panels. Scatter labels remain inside their plot; logo HBars reserve a measured left overlay region; Sankey owns node layout rather than cartesian grid geometry. New exceptions require route-level visual verification in both themes.

Treemap labels use the shared `TreemapLabelContrast` ECharts extension. Choose black or white by relative-luminance contrast against the resolved tile fill, compositing transparent fills over their background. Parent headers use their own label background. Apply the same opaque text color to names and values, without text outlines or shadows. Register the extension for every treemap renderer and PNG exporter.

Treemap PNG exports use native ECharts labels only and disable animation on the treemap series, whose default overrides the global animation flag. Apply export label settings at series, level, and data-item scope because level settings can suppress series labels. Do not add a second text graphic layer over tiles. Verify that labels appear once and remain visible in nested and zoomed exports.

ECharts renders to canvas and cannot read `var()`: resolve canvas tokens through [`src/components/ECharts/shared/chartTheme.ts`](src/components/ECharts/shared/chartTheme.ts) — `useChartTheme(isThemeDark)` in components, `getChartTheme(isDark)` in plain functions. Never read `--chart-*` by hand and never reintroduce `isDark ? literal : literal` chrome forks. HTML tooltip options should use the shared tooltip class rather than resolved canvas colors. Remaining hardcoded colors should be data/series colors or documented product-specific exceptions, not axis, grid, legend, dataZoom, or tooltip chrome.

## Utility & reuse policy

- **Reuse lives in React components** (Card, Button, …), not in `@apply` composites. A component owns its class string in one place. [`src/ui/Card.tsx`](src/ui/Card.tsx) is the card surface — required constrained `padding` choices, `className` for layout placement only; all new cards use it, existing cards migrate during page sweeps.
- `@utility` is allowed only for **small, flat, variant-free** declaration sets (a border color, a type style). No `@apply` chains with embedded `hover:`/`dark:` variants — that pattern re-emits its full body per variant and is why the `dialog`/`pro-btn-*` compatibility utilities are kept frozen, not multiplied.
- Prefer registered utilities (`bg-surface`) over arbitrary-value syntax (`bg-(--bg-surface)`) in all new code.

## Do's and Don'ts

- Do rank text with the tier tokens; don't hardcode grays (`#666`, `#919296`).
- Do use `text-data-up/down` for movement; don't signal direction with color alone where it matters — pair with sign or arrow.
- Do flip modes via tokens; never write `dark:text-[#hex]`.
- Don't introduce a new token for a one-off value — either it maps to an existing semantic or it goes to design for a library decision first.
- Don't use `bg-surface-elevated-*` as page-level fills; they are for nested emphasis.
- Don't restate brand blue, premium gold, or any palette hex inline; if a needed token is missing, that's a design.md/library gap to raise, not a literal to paste.
- Do pair every width-only border/divide utility (`border`, `border-t`, `divide-y`, …) with a color source (`border-subtle`, `border-medium`, an inline `style={{ borderColor }}`, …). The Tailwind v3 default-border-color compatibility shim was removed from `tailwind.css` (2026-07-10) after an audit found zero implicit consumers, so a colorless border renders `currentColor` — near-white in dark mode.
- Do use Tailwind v4 spellings: trailing important (`px-1!`), `rounded-sm`, `outline-hidden`, `x-(--var)`, `size-*`, `truncate`, `bg-linear-to-*` — the v3 forms are deprecated compat and ratcheted.
- `bun scripts/policies/check-design-tokens.mjs` enforces the above as a ratchet: existing debt is baselined in `scripts/policies/design-token-baseline.json`, and the check fails when any tracked token, radius, border-color, or named-typography conflict count increases. After removing debt, run `bun scripts/policies/check-design-tokens.mjs --update` to lock in the improvement.
